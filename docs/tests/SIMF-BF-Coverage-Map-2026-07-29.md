# SIMF — business-flow coverage map (BF-01..09, BF-15)

_Generated 2026-07-29 by a 10-agent mapping pass with an adversarial verification stage. One agent per flow read the flow definition and searched every test suite; a second stage tried to REFUTE each `COVERED` claim by opening the cited test and reading its assertions._

## The headline

| | |
|---|---|
| Scenarios mapped | **128** across 10 flows |
| COVERED | 2 |
| PARTIAL | 106 |
| GAP | 17 |
| NOT-APPLICABLE | 3 |
| `COVERED` claims **refuted** on verification | **15** |

**Almost nothing is covered end to end.** The verification stage refuted the large majority of `COVERED` claims, and the reason was the same nearly every time: the cited tests are real, un-skipped and assert what they say, but each asserts one *leg* of a journey. A business flow is a chain across surfaces, and a chain is not tested by testing its links separately — the joins are where these flows actually break.

That is the honest state of it: this repo has ~3,700 tests and deep coverage of individual endpoints, and close to zero coverage of the journeys those endpoints exist to serve.

`PARTIAL` is therefore the normal result here, not a disappointing one. Read it as: *the pieces are tested, the journey is not.*

## How to use this

- **`GAP`** — nothing asserts it. These are the cheapest real wins.
- **`PARTIAL`** — the evidence column names what IS asserted and what is not. Most need a single test that drives the existing legs in sequence.
- **`NOT-APPLICABLE`** — the feature is deferred (the G-OI-2 geofence chain, the live-video provider, the D6 statistics list). Not a gap; do not schedule.
- Evidence cites only files the mapping agent opened. Where a claim was refuted, the refutation is quoted under the row.

### BF-15 — what the mapping turned up

> FOUR flow-doc-vs-code contradictions, all confirmed by reading the source:
>
> 1. MEETING KINDS NOW NAVIGATE - the doc is stale. BF-15-003's "no-navigation kinds (null clickUrl)" table lists MeetingScheduled and MeetingCancelled -> null, and the Notes section repeats it ("Meeting + rejection kinds do not navigate... Only BookingConfirmed and the five rating kinds navigate"). The code says the opposite: src/Backend/SIMF.Application/Notifications/NotificationKindCatalog.cs:101-104 returns "/meetings" for MeetingScheduled, MeetingCancelled, MeetingRequestConfirmed and MeetingReminder (comment "QA A27 - every meeting-lifecycle tile is navigable"), and tests/SIMF.Api.Tests/NotificationKindCatalogTests.cs:85-116 asserts exactly that (ClickUrlFor_every_meeting_lifecycle_kind_opens_the_meetings_page, plus a ratchet ClickUrlFor_covers_every_kind_in_the_Meetings_group that fails the build if any Meetings-group kind has a null clickUrl). MeetingRequested also gained "/meeting-confirm?requestId={id}". A test written from the doc's table would fail.
>
> 2. THE ALLOWLIST HAS FOUR ENTRIES, NOT TWO. The doc says the allowlist is { /rate, /badge } in the prose, in BF-15-001, BF-15-005, BF-15-006 and in the Notes. src/Mobile/simf_app/lib/features/notifications/notifications_screen.dart:31-40 is { /rate, /badge, /meeting-confirm, /meetings }. BF-15-006's "a foreign clickUrl is ignored" is still the right rule, but a test asserting that /meetings is rejected would be wrong.
>
> 3. BF-15-001'S TRIGGER DOES NOT EXIST. The scenario opens "the visitor self-picks a seat and the reservation is confirmed / Then a notification row is created with kind BookingConfirmed". A repo-wide grep for BookingConfirmed in src/ returns only 9 files - the enum (SIMF.Common/Enums/NotificationKind.cs:91), the catalog, two resx resource files, and Flutter UI/test files. There is NO dispatch site anywhere in the backend. tests/SIMF.Api.Tests/SeatReservationsTests.cs:83-88 asserts the opposite explicitly: after reserving, it queries for a BookingConfirmed row and asserts `Assert.Null(note); // reservation-only fires no notification on reserve`. So the golden journey as written cannot be executed against this build. Either the flow prose predates the reservation-only rework, or the dispatch is a genuine product gap - worth an owner ruling.
>
> 4. THE DISPATCHER'S STAMPING IS ENTIRELY UNTESTED, and so is the wire contract the flow is named after. NotificationDispatcher.cs:63-66 does the `request.ClickUrl ?? NotificationKindCatalog.ClickUrlFor(...)` / `request.Group ?? NotificationKindCatalog.GroupFor(...)` fallback, but the persisted column name GroupCode appears in ZERO .cs test files (repo-wide grep hits only src/, migrations, DECISIONS_LOG.md and two .trx result files). NotificationTests.Dispatcher_writes_a_DB_row_when_called only checks that unread-count went to 1. On the client side, src/Mobile/simf_app/test/features/notifications/notification_models_test.dart never puts 'group' or 'clickUrl' in a JSON fixture, so NotificationItem.fromJson's decoding of those two keys (notification_models.dart:124-125) is never exercised. The whole point of BF-15 - "group + clickUrl are server-decided and each surface renders from those server values" - is proven only at the pure-function catalog level and at the widget level with hand-built objects; the two integration seams between them have no test.
>
> Smaller observations:
>
> 5. The doc's group inventory (BF-15-002) is missing eight kinds that now have catalog arms: BookingReleased (Bookings), SessionCancelled (Sessions), ParticipationDocumentDecided, BadgeUpdateDecided, AdminAnnouncement, ExhibitorLeadCaptured (all Account), MeetingRequested and MeetingReminder (Meetings). The exhaustive GroupFor_covers_every_defined_kind test does keep them from falling into the null bucket, so the doc is incomplete rather than wrong.
>
> 6. The doc's Note "MeetingRequestConfirmed has no client-side fallback arm" is STILL accurate - notifications_screen.dart:55-60 lists MeetingScheduled / MeetingCancelled / MeetingRequested / MeetingReminder but not MeetingRequestConfirmed, so a legacy row with a null server group would still fall to 'Account'. Nothing tests it.
>
> 7. BF-15-010's stated gate is imprecise. The doc says the endpoints "need a sub claim (401 otherwise)". They actually carry Policies(nameof(AuthorizationPolicies.RequireApprovedAccount)) (NotificationEndpoints.cs:23,52,84,112,144), so an approved-account check fires before the sub-claim guard - a signed-in-but-Pending visitor gets 403, not 401, and that is the only auth assertion that exists. Also, unread-count deliberately has no RequireRateLimiting("auth") while the other four do, which matches the doc's parenthetical.
>
> 8. Do not confuse the two /account/notifications routes. BF-15 means the Control Panel page (src/ControlPanel/.../Components/Pages/Account/Notifications.razor:6-8, @page + @attribute [Authorize] - still present). The WEBSITE's /account/notifications was deleted on 2026-07-27 under D-774, and tests/SIMF.Web.Tests/PublicSiteRoutesTests.cs:28 now ratchets it out (Removed_auth_and_account_routes_are_not_routable). A browser test that opens /account/notifications on the public site will 404 by design.
>
> 9. BF-15-004's unknown-kind example uses severity "Warning" -> accent + priority_high_rounded; the existing Flutter test asserts the Error branch (danger + close_rounded). Both are correct against notification_category_icon.dart:96-111 - just a different arm of the same fallback.
>
> 10. Nothing in this flow touches the known project deferrals (G-OI-2 geofence chain, D7 live video, D6 statistics), so no scenario here is NOT-APPLICABLE.
