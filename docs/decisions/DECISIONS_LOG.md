# SIMF Decisions Log

Implementation decisions and assumptions that are not (or not yet) captured in a
controlled document. Each entry is dated and explains the reasoning, per the
project working rules. Newest first.

When a decision is later absorbed into a controlled document, the entry keeps a
note pointing to that document.

| ID | Date | Decision | Reasoning |
|----|------|----------|-----------|
| D-023 | 2026-05-22 | Automated tests for the frontend login increment cover the logic-bearing code — `SimfAuthClient` and `SimfAuthSession` — with xUnit (`tests/SIMF.ApiClient.Tests`). The `Simf*` components and the authentication pages are verified by running the apps and capturing screenshots (light and dark themes, the field-validation state). | The API client (envelope handling, transport-failure mapping) and the session holder (`MaskEmail`, state transitions) carry real logic and are unit-tested. The components are largely declarative markup; rendering tests with bUnit are a tracked follow-up rather than a blocker for a first frontend increment, and the visual verification is the recorded evidence in the meantime. |
| D-022 | 2026-05-22 | The authentication pages ship with English interface text. Full Arabic/English resource-file localisation (SIMF-CPD-001 §10) is delivered with the Control Panel base-shell increment. | The `Simf*` components are built RTL-ready — CSS logical properties throughout — and the `SimfLanguageSwitch` component exists; only the resource files and the culture-cookie wiring are deferred. SIMF-CPD-001 §10 frames localisation as a shell-level concern (the language switch lives in the top bar, remembered per user), so it is delivered once, with the shell, rather than half-built for the login pages and redone. This matches the agreed frontend-increment scope. |
| D-021 | 2026-05-22 | The `Simf*` login components are built as semantic HTML styled by `theme.tokens.css`, not as MudBlazor wrappers. | The approved 2026-05-20 design decision makes `Simf*` the UI vocabulary and explicitly overrides the earlier "MudBlazor only" recommendation. Plain HTML + token CSS renders identically under server-side rendering and Interactive Server, needs no JavaScript for the form tier, and gives full control of the brand and of RTL. MudBlazor stays mandated for the Control Panel's rich interactive widgets — data tables, dialogs, navigation — and is introduced with the CP base-shell increment. |
| D-020 | 2026-05-22 | `theme.tokens.css` carries a proposed navy-derived dark-theme token set (a `[data-theme="dark"]` block) so the Control Panel and Website ship a working dark theme now. | SIMF-CPD-001 §8.5 / OI-1 leaves the dark-theme token values to be reviewed. The values here are **proposed for client review**, consistent with how SIMF-CPD-001 §8.4 already treats the derived functional tokens. Only token values change between themes; no component or page is rewritten, so a reviewed change is a single-file edit. |
| D-019 | 2026-05-22 | Frontend project layout: `src/ControlPanel/SIMF.ControlPanel` (the CP app), `src/Website/SIMF.Web` (the Website), `src/Shared/SIMF.Components` (the `Simf*` Razor component library), `src/Shared/SIMF.ApiClient` (the typed Login-API client), `tests/SIMF.ApiClient.Tests`. | SIMF-SES-001 §4.1 fixes a `/src/ControlPanel` folder and the top-level layout but does not name the projects and gives the Website no folder. The component prefix is `Simf` — matching the SIMF acronym and every existing `SIMF.*` project; the 2026-05-20 design-decision note recorded it as `Smif*`, a typo, corrected here. |
| D-018 | 2026-05-22 | The public Website ships a sign-in / forgot-password / reset-password flow now, ahead of SIMF-FDS-001 OI-3. | OI-3 records "whether the website offers sign-in" as still to be confirmed with the client; the owner instructed the Website login be built. Recorded so OI-3 is closed by a deliberate decision, not by omission. If the client decides the Website offers no sign-in, the Website authentication pages are removed — the `Simf*` library and the Control Panel are unaffected. |
| D-017 | 2026-05-22 | The Control Panel is a Blazor Server application (Interactive Server render mode). The public Website is server-side rendered by default, with the authentication pages opting into Interactive Server. | SIMF-CPD-001 §4 mandates Blazor + MudBlazor for the Control Panel but leaves the render flavour unspecified; the owner chose Interactive Server. It keeps the JWT on the server (the token never reaches the browser, and the API call is server-to-server with no cross-origin concern) and matches MudBlazor's interactivity model. The Website is SSR for its future public content; the authentication pages need interactivity — a submitting state, inline validation, show/hide password — so they are Interactive Server islands on an otherwise SSR site. |
| D-016 | 2026-05-22 | **Deferred hardening.** `AccountCode` rows (the six-digit email-verification, sign-in-OTP and password-reset codes) are stored in plaintext. Hashing the codes at rest is recorded as a pre-freeze hardening item. | The codes are short-lived (10 minutes for password reset), single-use (`ConsumedAt` is set on first valid use), and attempt-capped (5 wrong tries per code). A database-read attacker who already has the `AccountCode` table also has the `Users` table and the security stamps, so plaintext codes are not the weakest link for that threat. Hashing them (same SHA-256 pattern as `OpaqueToken`) is still worth doing before freeze for defence-in-depth and is logged here so it is not lost. |
| D-015 | 2026-05-22 | **Accepted risk.** The password-reset six-digit code has a bounded brute-force surface — a per-code attempt cap of 5 and a per-account re-issue cap of 5 per hour — giving at most about 25 guesses per hour against a 10⁶ code space. This is accepted rather than further tightened. | Consistent with the sign-in-OTP bound already accepted in D-008 and D-011. About 25 guesses/hour against a six-digit code is a ~1-in-40 000 chance per hour; combined with the 10-minute code lifetime and per-IP rate limiting the residual risk is acceptable for the Login API. Revisit if the reset model changes. |
| D-014 | 2026-05-22 | Reset-password sets the new password with `RemovePasswordAsync` + `AddPasswordAsync` inside a transaction, rather than ASP.NET Identity's `GeneratePasswordResetTokenAsync` / `ResetPasswordAsync`. | The Identity reset-token provider (`AddDefaultTokenProviders`) is not available in the Infrastructure class library — it ships with the ASP.NET Core shared framework, not the `Microsoft.Extensions.Identity.*` packages. SIMF's own six-digit `PasswordReset` code is the authorisation; remove-then-add still runs the Identity password validators and rolls the security stamp, and the transaction keeps the pair atomic so a rejected password leaves the old one intact. (TOTP verification likewise uses Otp.NET for the same packaging reason — increment 4b.) |
| D-013 | 2026-05-22 | The `OnTokenValidated` security-stamp check does one database read per authenticated request. Refresh-token row pruning and an `OperationLog` severity column are deferred to a later operations task. | The per-request stamp read is the cost of instant access-token revocation on sign-out; with few protected endpoints today it is acceptable. At Control Panel scale it is revisited with a short-TTL cache or the ASP.NET Identity `SecurityStampValidator` interval. Revoked/expired refresh-token rows accumulate (kept for the reuse-detection forensic trail) — a retention prune and a `Severity` column for SIEM alerting are an operations-hardening item, recorded so they are not lost. |
| D-012 | 2026-05-22 | Sign-out ends **every** session for the account — it revokes all of the account's refresh tokens and rolls the security stamp — rather than only the current session. | The access token is stateless and cannot be revoked individually; the security stamp is the revocation signal and is per-account, so rolling it necessarily ends every session. Revoking all refresh tokens as well keeps the two consistent. A per-session sign-out would need a session identifier in the token and is not in the Login API scope. |
| D-011 | 2026-05-22 | The sign-in second-factor ticket and the emailed OTP code are correlated by user id and "latest unconsumed", not bound by a foreign key. | The increment-4b security review suggested an FK from the OTP code to the ticket. The OTP brute-force surface is instead bounded by two enforced caps — the per-ticket attempt cap (5) and the per-account sign-in-OTP re-issue cap (5 per hour) — together limiting guessing to about 25 codes/hour against a six-digit code, independent of the binding. The FK is a structural-clarity improvement, deferred; revisit if the sign-in OTP model grows. |
| D-010 | 2026-05-21 | Sign-in succeeds for an account in `EmailVerified`, `PendingApproval` or `Approved` state; it is blocked for `Registered` (email not verified) and for `Disabled` / `Rejected`. The access a not-yet-`Approved` user then has is an authorisation concern, not a sign-in block. | SIMF-RPM-001 §10 states a `PendingApproval` visitor signs in and sees a limited status view. SIMF-API-001 OI-4 (gate D1) is the authoritative open item on not-yet-approved access; this is the sign-in-layer interpretation pending its closure. |
| D-009 | 2026-05-21 | The operation log is written to the application database with a Serilog file sink; a SIEM / central-log integration, alerting rules, a retention policy and append-only (tamper-evident) enforcement are **not** part of increment 4a — they are scheduled as a separate monitoring task before go-live. | Increment 4a delivers the durable, queryable audit record. The increment-3 threat review and decision D-006 expect *monitoring* on top of the log; that layer (forwarding, alerting, retention, tamper-evidence) is a distinct piece of work, recorded here so it is not mistaken for done. |
| D-008 | 2026-05-21 | The per-account verification-code resend cap is enforced best-effort by a count-then-issue check; it is not made fully concurrency-safe. | A plain transaction would not close the check-then-act race (two concurrent resends each reading a count below the cap) without SERIALIZABLE isolation, which is disproportionate for a soft five-per-hour cap. The hard controls are the per-IP rate limiter and the per-code attempt cap; the resend cap is a supplementary account-keyed limit. An exact-concurrent burst may yield a few extra codes — still bounded. |
| D-007 | 2026-05-21 | An unhandled 500 error is logged through Serilog (with its correlation id) but is not written to the operation-log database table. | The operation log is itself a database write; if the database is the failing dependency, auditing a 500 to it would fail too. Security-relevant business events (sign-up, verification, resend, super-admin seed) are written to the operation log by the services; infrastructure failures are captured in the structured application log instead. |
| D-006 | 2026-05-21 | **Accepted risk.** The account-creation endpoints reveal whether an email address is registered — sign-up returns 409 `AUTH_EMAIL_ALREADY_REGISTERED` for an existing address, and verify-email / resend-code return 404 `AUTH_ACCOUNT_NOT_FOUND` for an unknown one. The owner chose to accept and document this rather than make the responses non-revealing. | The increment-3 security review raised account enumeration on these endpoints. The duplicate-email 409 is kept for registration usability. The exposure is accepted on condition of the compensating controls in increment 4 — strict per-account and per-IP rate limiting, and the audit/operation log with monitoring for enumeration patterns. SIMF-API-001 §12.4 and SIMF-FDS-001 §5.1–5.3 already specify this behaviour, so no controlled-document change is needed. Revisit if the threat picture changes. |
| D-005 | 2026-05-21 | ASP.NET Core Identity enforces the SIMF-API-001 §12.5 password baseline (length 8, at least one digit); the request validators add the remaining rules (a letter, not equal to the email). | The increment-3 security review found that leaving Identity's password options permissive meant any credential path not going through the FluentValidation validator — the super-admin seeder, the future password-reset flow — got an effective 1-character policy. §12.5's "enforced in one place" is therefore read as defence-in-depth: the baseline at the Identity credential layer, the full policy with field-level messages in the validators. |
| D-004 | 2026-05-21 | Per-endpoint rate limiting (FastEndpoints `Throttle`) is deferred from increment 3 to increment 4. | FastEndpoints' `Throttle` returns 403 when a request carries no `X-Forwarded-For` header, which breaks direct (non-proxied) callers and the test host. Rate limiting belongs in the increment-4 middleware pipeline (SIMF-Sprint1 plan §7), applied uniformly. |
| D-003 | 2026-05-21 | .NET test assertions use xUnit's built-in `Assert`; FluentAssertions is not adopted. | FluentAssertions v8 carries a commercial-licence model that, combined with the warnings-as-errors build, risks breaking the build. xUnit's own assertions are sufficient and dependency-free. Recorded in SIMF-TST-001 v1.1 §5. |
| D-002 | 2026-05-21 | The solution uses the `.slnx` solution format (`SIMF.slnx`). | The .NET 10 SDK defaults `dotnet new sln` to the new XML solution format. Kept rather than forcing the legacy `.sln` format. |
| D-001 | 2026-05-21 | FastEndpoints registration (`AddFastEndpoints` / `UseFastEndpoints`) is deferred from increment 1 to increment 3. | FastEndpoints throws at startup when no endpoint is declared, and the first endpoint arrives in increment 3 (the authentication endpoints). The `FastEndpoints` package stays referenced by `SIMF.Api`; only the wiring is deferred. |
