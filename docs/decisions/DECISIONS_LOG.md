| D-041 | 2026-05-23 | Recovery from a lost authenticator + lost recovery codes is **admin-driven**, not self-service email. A new `POST /api/v1/admin/users/reset-two-factor` endpoint, gated on the `Administrator` role, wipes the target's authenticator key, recovery codes, `TwoFactorEnabled` flag, security stamp and refresh tokens, and queues a notification email to the target. The actor cannot reset themselves (use the profile-page Disable instead) and cannot reset another `Administrator` (separation of privileges — the super-administrator's recovery path stays out-of-band via the seeder + `appsettings.json` re-pair). A mandatory free-text reason (10–500 chars) is captured in the audit row alongside both actor and subject user ids (new `OperationLog.ActorUserId` column). The CP page is `/admin/reset-2fa` with a `[Authorize(Roles = "Administrator")]` gate, a confirmation dialog, and bilingual strings. Operator-level SQL reset stays documented as the fallback for the super-administrator (see `docs/SIMF-OPS-001-Recovery-Procedures.md`). Email-as-self-service recovery (the alternative considered) was **rejected** for SIMF's defence / MoD-confidential context: email isn't a strong second factor, and treating an email account as an MFA bypass is policy-wrong for any role-holder. Visitor self-recovery isn't needed today because visitors don't have 2FA opt-in. | Mirrors the enterprise SSO baseline (Okta / Azure AD admin-driven reset). The new `ActorUserId` field is the cleanest seam for future privileged actions (account approve / delete, role assignment) and is nullable so every existing audit row stays valid. The Administrator-vs-Administrator block is the standard "no peer demotion" rule — it stops a compromised admin from neutralising the rest of the admin tier. Notification email is the out-of-band signal that defeats silent abuse. The reset uses the same internal wipe `TotpEnrollmentService.DisableAsync` already does, plus the recovery-code revoke + refresh-token revoke + security-stamp roll, all in one transaction. Six integration tests pin the contract; an admin-reset failure (self-reset, admin-vs-admin, missing target) emits `Admin.TwoFactorResetFailed` with the error code so the SIEM can alert on abuse attempts. |
| D-040 | 2026-05-23 | TOTP enrolment issues **ten single-use recovery codes** as a lost-authenticator fallback. Codes are 10-character Crockford-base32 (no `0/O/1/I/L/U`) printed as `XXXXX-XXXXX`; ~49 bits of entropy each; stored as SHA-256 hex hashes in a new `TotpRecoveryCodes` table; revealed plaintext exactly once in the `TotpConfirmResponse` (and in `RecoveryCodesResponse` on regenerate) and never again. A user signs in with a recovery code at the new `POST /api/v1/auth/verify-recovery-code` endpoint using the same MFA-token ticket the TOTP step uses — a recovery code is an *alternative* second factor, not a 2FA bypass. Regenerating wipes the previous batch atomically; disabling 2FA wipes the codes too. **Same sign-in flow choice update**: the second-factor kind is now TOTP for **any user with an authenticator key**, not only role-holders, so a visitor who enrols in 2FA from the profile page actually signs in via TOTP (and can also recover via recovery code). The visitor email-OTP path is preserved for users with no authenticator key. Wrong recovery-code attempts call `AccessFailedAsync` (same lockout budget as a wrong TOTP), and the existing ticket attempt-count gates brute force per session. Audit events: `Totp.RecoveryCodesGenerated`, `Totp.RecoveryCodesRegenerated`, `Totp.RecoveryCodeUsed`, `Totp.RecoveryCodeFailed`. Profile page surfaces "X of 10 remaining" with a "Regenerate" button and a low-codes warning when ≤ 3 remain. | OWASP / GitHub / Microsoft / Google industry baseline. The lost-authenticator gap had no in-app recovery before this — operators were left with direct SQL or a re-seed for the super-admin (see "How to recover" investigation 2026-05-23). The Crockford alphabet matches what makes a code easy to read off paper. Hashing with SHA-256 (not Argon2) is the same scheme `RefreshToken` and `SecondFactorToken` use — high-entropy tokens don't need a slow KDF. Decision to base the second-factor kind on the authenticator-key presence (not just role) is small in code but materially correct: a visitor who has opted into TOTP must sign in via TOTP, otherwise the recovery flow would be unreachable for them. The legacy role-only path stays as a fallback for any pre-enrolment user. Existing visitor integration tests opt in by calling `EnableTwoFactor`, which sets only `TwoFactorEnabled` (no authenticator key) — those still go through email-OTP, so the change is back-compatible. |
