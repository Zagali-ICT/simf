# SIMF Decisions Log

Implementation decisions and assumptions that are not (or not yet) captured in a
controlled document. Each entry is dated and explains the reasoning, per the
project working rules. Newest first.

When a decision is later absorbed into a controlled document, the entry keeps a
note pointing to that document.

| ID | Date | Decision | Reasoning |
|----|------|----------|-----------|
| D-010 | 2026-05-21 | Sign-in succeeds for an account in `EmailVerified`, `PendingApproval` or `Approved` state; it is blocked for `Registered` (email not verified) and for `Disabled` / `Rejected`. The access a not-yet-`Approved` user then has is an authorisation concern, not a sign-in block. | SIMF-RPM-001 §10 states a `PendingApproval` visitor signs in and sees a limited status view. SIMF-API-001 OI-4 (gate D1) is the authoritative open item on not-yet-approved access; this is the sign-in-layer interpretation pending its closure. |
| D-009 | 2026-05-21 | The operation log is written to the application database with a Serilog file sink; a SIEM / central-log integration, alerting rules, a retention policy and append-only (tamper-evident) enforcement are **not** part of increment 4a — they are scheduled as a separate monitoring task before go-live. | Increment 4a delivers the durable, queryable audit record. The increment-3 threat review and decision D-006 expect *monitoring* on top of the log; that layer (forwarding, alerting, retention, tamper-evidence) is a distinct piece of work, recorded here so it is not mistaken for done. |
| D-008 | 2026-05-21 | The per-account verification-code resend cap is enforced best-effort by a count-then-issue check; it is not made fully concurrency-safe. | A plain transaction would not close the check-then-act race (two concurrent resends each reading a count below the cap) without SERIALIZABLE isolation, which is disproportionate for a soft five-per-hour cap. The hard controls are the per-IP rate limiter and the per-code attempt cap; the resend cap is a supplementary account-keyed limit. An exact-concurrent burst may yield a few extra codes — still bounded. |
| D-007 | 2026-05-21 | An unhandled 500 error is logged through Serilog (with its correlation id) but is not written to the operation-log database table. | The operation log is itself a database write; if the database is the failing dependency, auditing a 500 to it would fail too. Security-relevant business events (sign-up, verification, resend, super-admin seed) are written to the operation log by the services; infrastructure failures are captured in the structured application log instead. |
| D-006 | 2026-05-21 | **Accepted risk.** The account-creation endpoints reveal whether an email address is registered — sign-up returns 409 `AUTH_EMAIL_ALREADY_REGISTERED` for an existing address, and verify-email / resend-code return 404 `AUTH_ACCOUNT_NOT_FOUND` for an unknown one. The owner chose to accept and document this rather than make the responses non-revealing. | The increment-3 security review raised account enumeration on these endpoints. The duplicate-email 409 is kept for registration usability. The exposure is accepted on condition of the compensating controls in increment 4 — strict per-account and per-IP rate limiting, and the audit/operation log with monitoring for enumeration patterns. SIMF-API-001 §12.4 and SIMF-FDS-001 §5.1–5.3 already specify this behaviour, so no controlled-document change is needed. Revisit if the threat picture changes. |
| D-005 | 2026-05-21 | ASP.NET Core Identity enforces the SIMF-API-001 §12.5 password baseline (length 8, at least one digit); the request validators add the remaining rules (a letter, not equal to the email). | The increment-3 security review found that leaving Identity's password options permissive meant any credential path not going through the FluentValidation validator — the super-admin seeder, the future password-reset flow — got an effective 1-character policy. §12.5's "enforced in one place" is therefore read as defence-in-depth: the baseline at the Identity credential layer, the full policy with field-level messages in the validators. |
| D-004 | 2026-05-21 | Per-endpoint rate limiting (FastEndpoints `Throttle`) is deferred from increment 3 to increment 4. | FastEndpoints' `Throttle` returns 403 when a request carries no `X-Forwarded-For` header, which breaks direct (non-proxied) callers and the test host. Rate limiting belongs in the increment-4 middleware pipeline (SIMF-Sprint1 plan §7), applied uniformly. |
| D-003 | 2026-05-21 | .NET test assertions use xUnit's built-in `Assert`; FluentAssertions is not adopted. | FluentAssertions v8 carries a commercial-licence model that, combined with the warnings-as-errors build, risks breaking the build. xUnit's own assertions are sufficient and dependency-free. Recorded in SIMF-TST-001 v1.1 §5. |
| D-002 | 2026-05-21 | The solution uses the `.slnx` solution format (`SIMF.slnx`). | The .NET 10 SDK defaults `dotnet new sln` to the new XML solution format. Kept rather than forcing the legacy `.sln` format. |
| D-001 | 2026-05-21 | FastEndpoints registration (`AddFastEndpoints` / `UseFastEndpoints`) is deferred from increment 1 to increment 3. | FastEndpoints throws at startup when no endpoint is declared, and the first endpoint arrives in increment 3 (the authentication endpoints). The `FastEndpoints` package stays referenced by `SIMF.Api`; only the wiring is deferred. |
