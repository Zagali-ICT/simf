# Pending global-doc merges — `OP-SUPERADMIN-SEED` (Track A, item A4)

The super-admin seed failed **silently** when the configured temp password
violated the password policy, leaving a Control Panel nobody could sign into.

## DECISIONS_LOG

| D-NEXT | 2026-07-31 | **A failed super-admin seed fails the boot in Production (`OP-SUPERADMIN-SEED`).** `IdentitySeeder.CreateSuperAdminAsync` logged the Identity errors and returned `null`; `SeedAsync`'s caller saw the `null` and returned. The API then finished starting and reported healthy with **no super-administrator row at all**, so the Control Panel had no way in and nobody found out until someone tried to sign in. `Program.cs`'s existing production guard does not cover this: it rejects only the exact committed **default** temp password, so any custom value that merely breaks the policy (too short, no digit, no symbol) walks straight past it into the silent path. **Fix:** when `CreateAsync` fails and `hostEnvironment.IsProduction()`, throw an `InvalidOperationException` naming the setting (`SuperAdmin:TempPassword`) and carrying `result.Errors`, so the operator sees **which** policy rule the configured value broke instead of guessing. Outside Production the log-and-skip stands deliberately — a developer on a half-configured box must still be able to start the app, and turning that into a hard stop would trade one outage for another. `IHostEnvironment` was already injected; no new dependency, no schema change, no contract change. **Test:** `tests/SIMF.Api.Tests/SuperAdminSeedFailureTests.cs` drives the real seeder with only `IHostEnvironment` and `IOptions<SuperAdminOptions>` substituted (via `ActivatorUtilities`) rather than booting a second host under Production, which would trip five unrelated production guards and prove nothing about this one. Three cases: throws in Production on a policy-violating password with the reasons in the message; logs-and-skips in Development; and — the case that stops the fix becoming a new outage — still seeds normally in Production when the password is compliant. | The failure mode was not "the seed broke" but "the seed broke and the system said it was fine". A boot that comes up healthy with no administrator is a failed deployment pretending to be a successful one, and the only place that is cheap to detect is at boot. |
