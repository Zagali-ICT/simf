# C1 — `#10-phase4` — badge self-claim captures no profile data

## DECISIONS_LOG

### D-NEXT — Badge self-claim captures the claimer's profile (#10 phase 4)

**Context.** A bulk badge run (D-758) mints a placeholder account: a generated
display name such as "VIP #3", a profile stub with `NationalityId = 0` and no
interests. `BadgeActivationCompleteRequest`
(`src/Shared/SIMF.Contracts/Authentication/BadgeAuth.cs`) carried only `QrId`,
`Code`, `NewPassword`, `ConfirmPassword`, and
`BadgeAuthService.CompleteActivationAsync` verified the code, set the first
password and attached the stashed email — but never touched the placeholder
`UserProfile`. A claimed badge kept its generated name and a zero nationality
permanently, and self-claim is the only moment the real holder is at the keyboard.

**Decision.** Extend the complete-activation request with four optional profile
fields — `EnglishName`, `ArabicName`, `NationalityCode`, `InterestIds` — and fill
the placeholder profile inside `CompleteActivationAsync`. Promote the captured name
to the account's `DisplayName` as well, but only inside the Identity transaction
that already runs there.

**Consequences / constraints honoured.**

- **No Identity schema change.** The profile lives on `SIMF_App`, the account on
  `SIMF_Identity`; they are written as two separate units of work, because D-157
  forbids a transaction spanning both databases.
- **Append-only wire (D-219).** All four fields are optional with defaults, so a
  client that sends none activates exactly as before. That is the path the shipped
  Flutter app takes until Track D adds the capture step.
- **Validate before any write.** The country code and interest ids are resolved and
  checked against the live App-DB lookups up front — alongside the existing
  pending-email re-check — so a bad payload cannot half-activate a badge. Same error
  codes as the ordinary profile upsert: `PROFILE_NATIONALITY_UNKNOWN`,
  `INTEREST_INVALID`.
- **Ordering: profile first, password second.** If the password step fails
  afterwards, the badge is still unactivated and the holder retries; the profile
  write is idempotent and the retry overwrites it. The reverse order would leave an
  activated account whose retry is refused by `EnsureNotAlreadyActivated`, with the
  placeholder never filled.
- Interests are **added**, never removed — the holder edits the full set later on
  the profile screen.

**Rejected alternative.** A separate post-activation "complete your profile" call.
It would work, but it re-opens the window this defect is about: the holder is signed
out immediately after activation, so anything not captured here is captured never.

## Files changed

- `src/Shared/SIMF.Contracts/Authentication/BadgeAuth.cs` — four appended optional fields.
- `src/Backend/SIMF.Application/IdentityAccess/BadgeAuthService.cs` — `IUserProfileRepository`
  injected; `ResolveNationalityIdAsync`, `ResolveInterestIdsAsync`,
  `FillPlaceholderProfileAsync`, `FirstNonBlank` added; display-name promotion inside
  the existing Identity transaction.
- `src/Backend/SIMF.Api/Endpoints/Auth/Validators/BadgeAuthValidators.cs` — shape rules
  for the new fields (max lengths mirroring `UserProfileConfiguration`, ISO-code shape,
  the 1-10 interest cap).
- `tests/SIMF.Api.Tests/BadgeSelfClaimProfileTests.cs` — new, 5 facts.
- `docs/tests/e2e/api-badge-self-claim-profile.md` — new catalogue.

## Ownership note for the orchestrator

`SIMF.Contracts/Authentication/**`, `SIMF.Application/IdentityAccess/**` and
`SIMF.Api/Endpoints/Auth/**` are excluded from Track C's owned set (they belong to
Track A), but item C1 names those exact files as the fix. The three edits are
surgical and additive, in regions Track A's items (`SignInService`,
`JwtTokenService`, `AdminAccountService`, `IdentitySeeder`, `ITokenIssuer`
extraction) do not touch. Flagged so the merge is reviewed rather than assumed.
