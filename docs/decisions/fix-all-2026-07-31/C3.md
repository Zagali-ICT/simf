# C3 — `OA-D6` — public programme endpoint filters `?day=` only

## DECISIONS_LOG

### D-NEXT — Server-side category filter on the public programme list (OA-D6)

**Context.** `ListProgrammeSessionsRequest`
(`src/Backend/SIMF.Api/Endpoints/Programme/PublicSessionEndpoints.cs`) declared exactly
one property, `Day`, and `HandleAsync` parsed only that before calling
`service.ListAsync(day, ct)`. Any category or track filtering the app and website did
was client-side over the whole programme, even though `Session.CategoryId` and the
dynamic `SessionCategory` lookup (D-226) both already existed. Owner answer **Q7**:
build it.

**Decision.** Add an optional `Guid? CategoryId` to the request and thread it into
`IProgrammeSessionService.ListAsync` as a second nullable predicate — a plain equality
on the indexed FK, ANDed with the existing day window.

**Consequences / constraints honoured.**

- **Cache is unchanged.** The endpoint keeps `CacheOutput("PublicRead")`, which varies
  by **all** query keys, so every `?day=` × `?categoryId=` combination keys its own
  45-second entry automatically. No cache-policy edit, and a scenario
  (E2E-PCF-005) proves it rather than asserting it.
- **An unknown id returns an empty 200, never a 404.** A 404-vs-200 difference would
  turn the anonymous agenda into a category-id oracle.
- **Backward compatible.** The parameter is nullable with no default filter, so a
  client that never sends it sees exactly what it saw before.
- The interface signature gained the parameter in second position, so the two existing
  call sites (`ProgrammeSessionService.ListDaysAsync`,
  `AssistanceContextBuilder.BuildAsync`) were updated explicitly rather than silently
  rebinding a positional argument.

**Note on live behaviour.** `SessionCategory` ships EMPTY pending the client's
category list (D-226, open item OI-2). Until it is seeded, a request without
`?categoryId=` behaves exactly as before and one with it returns nothing. That is
correct, not a defect.
