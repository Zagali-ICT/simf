# Pending global-doc merges — `#2` (Track A, item A1)

Control-Panel sign-in minted a full access token on the password alone when no
second factor was enrolled. Owner decision **Q1 (2026-07-30): enrolment-first**.

## DECISIONS_LOG

| D-NEXT | 2026-07-31 | **Control Panel sign-in is enrolment-first: no session on the password alone (`#2`, owner decision Q1).** `SignInService.cs:175` was `if (!user.TwoFactorEnabled) { issue tokens }` with **no branch on `request.Audience`**, so a CP-audience administrator with 2FA off held a full admin session after one factor — and the production super-admin is recorded as 2FA-off, so this was live, not theoretical. **Fix:** before that fast path, a `SignInAudience.Cp` sign-in whose account has **no authenticator secret paired** is answered with a single-use `SecondFactorKind.TotpEnrolment` ticket (additive enum value `3`; the persisted column is `nvarchar(16)`, hence the short name) and **no tokens** — `SignInResponse` gains an appended nullable `TwoFactorEnrolmentToken` (append-only, mirroring D-206's `PasswordChangeToken`; the mobile wire contract is untouched). The holder enrols at two new `AllowAnonymous` endpoints, `POST /app/auth/totp/enrolment/start` (returns the QR + base32 key) and `/complete` (verifies the first code, activates the secret, mints the withheld session **stamped `amr=mfa`** and returns the D-040 recovery codes); both delegate to the existing `ITotpEnrollmentService`, so there is one enrolment implementation, not two. The Control Panel consumes them at a **new** page `/login/enrol-2fa` (`Components/Pages/Auth/TwoFactorEnrolment.razor` + code-behind) — `/account/totp-pairing` (D-096) could not serve this because it only re-renders an already-active secret and cannot create one. **Why 200-with-a-ticket rather than a 403:** `ApiError` carries no data payload, so a 403 could not hand back the ticket, and without a ticket the enrolment endpoints would have to accept a re-posted password. `ErrorCodes.AuthTwoFactorEnrolmentRequired` is instead the code returned when the presented ticket is unknown / expired (15 min) / consumed / attempt-exhausted, which is the state the caller is genuinely still in. **Anonymous surface:** both routes are added to the reviewed allow-list in `BusinessFlow13PermissionMatrixTests` with a per-entry justification (17 → 19 entries), so a 20th unauthenticated endpoint still breaks the build. **Configuration:** `IdentityLifecycle:RequireControlPanelTwoFactorEnrolment`, **default `true`** in `IdentityLifecycleOptions` and stated in `appsettings.json`. The general integration suite pins it **off** in `SimfApiFactory` because roughly 150 pre-existing admin fixtures read `Tokens.AccessToken` straight off a `Cp` password sign-in; the shipping posture is proved by `ControlPanelTwoFactorApiFactory` + `ControlPanelTwoFactorEnrolmentTests` — the same pattern already used for `FaceDetection:Enabled` and `DeviceKey:RequireStepUpForEnrol`. No schema change (the enum is persisted by name into an existing column), no permission (pre-token authentication surface). | Nobody may be locked out by a fix for a lockout-adjacent defect. A CP-audience carve-out that merely refused the token would have bricked every unenrolled admin, including the bootstrap super-admin; enrolment-first turns the refusal into a way in. It is also the precondition for `#2d` — see the next entry. |
