# C8 — `FR-1103` — movement / dwell / route tracking has no capture path

## DECISIONS_LOG

### D-NEXT — FR-1103 device-position capture, dwell aggregation and route projection

**Context.** There was no capture path and no data source. The only positional record
was `HallAttendance`, which is deliberately an arrival/departure PAIR — its own XML
doc says so: "never the raw coordinates or a continuous track (that is the deferred
movement/dwell feature, FR-1103)". A repo-wide search for `dwell|MovementTrack`
returned only that comment and its echo in `HallAttendanceService`. Owner decision
**Q6**: build it CP-configurable; it stays inert until halls are given boundaries,
which unblocks it without the G-OI-2 venue-boundary answer.

**Decision.** Add `DevicePositionPings` (additive table, migration
`20260731043000_FR1103_AddDevicePositionPings`) plus `IMovementTrackingService` with
three operations, and three endpoints:

| Route | Gate |
|---|---|
| `POST /api/v1/app/movement/pings` | approved account, **self-only**, rate-limited |
| `GET /api/v1/admin/movement/dwell` | `Attendance.View` |
| `GET /api/v1/admin/movement/route/{userId}` | `Attendance.View` |

**Inert by construction.** A ping binds to a hall by testing it against that hall's
configured geofence (`Hall.GeofenceCenterLat` / `Lon` / `RadiusMeters`, columns that
already existed for the D-240 arrival check). While no hall has one — the shipped
state — every ping lands with a null `HallId`, both reports return nothing, and the
capture response reports `matchedToHall: 0`, so a caller can *tell* the feature is
dormant rather than guess. Nothing else in the system reads these rows.

**Privacy posture.** Unlike `HallAttendance`, these rows DO hold raw coordinates — a
route projection cannot be derived without them — and GPS is sensitive personal data
(FDS-003 §10). Three controls follow, each with an E2E scenario:

1. Capture is **self-only**: the attendee id comes from the `sub` claim, never the
   body, so nobody can post another person's position.
2. Both reports are gated on `Attendance.View`.
3. Every report requires an explicit window, capped at 7 days
   (`MovementWindow.MaxSpan`). There is no unbounded read over raw GPS.

**No FK to `Hall` or `Session`**, even though both live in the same database. These
are telemetry rows written at device cadence; one must never be the reason a hall
cannot be edited or a session removed. The aggregation resolves names by lookup and
renders a nameless leg when an id no longer resolves.

**Aggregation rules that are judgement calls, not mechanics.**

- Dwell is the time **between consecutive pings**, so a single isolated ping
  contributes zero: it evidences presence, not duration.
- A gap longer than `MaxLegGap` (10 minutes) **ends the leg** rather than counting as
  dwell. Without this, a phone that lost signal at the door would read as an all-day
  attendee.
- Unmatched legs (the walk between halls) are **kept**, not dropped: dropping them
  would silently join two separate visits into one.
- When two geofences overlap, the **nearest containing** boundary wins, so resolution
  is deterministic rather than row-order dependent.

## Migration note for the orchestrator

Build agents are barred from running `dotnet ef`, so the migration, its `.Designer.cs`
and the model-snapshot entry were written by hand. The Designer was generated
mechanically from the patched snapshot (identical model body, `BuildModel` renamed to
`BuildTargetModel`, correct `[Migration]` id), so snapshot and Designer agree exactly —
the invariant `dotnet ef migrations add` maintains. Worth a `dotnet ef migrations list`
sanity check during the consolidated build.
