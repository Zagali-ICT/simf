# Pending global-doc merges — `itokenissuer-extraction` (Track A, item A5)

Token minting was duplicated across the auth paths, so the claim set and the
D-443 lifetime cap could drift between the ways into the system.

## DECISIONS_LOG

| D-NEXT | 2026-07-31 | **`ITokenIssuer` extracted — one place a SIMF session is minted (`itokenissuer-extraction`).** `SignInService.IssueTokensAsync` and `DeviceKeyService.MintTokensAsync` each carried their own copy of "resolve roles, resolve permissions, resolve the mobile app role, sign an access token, persist a refresh token with the D-443 absolute deadline". `DeviceKeyService`'s own XML doc had been flagging the duplication as a follow-up since D-172. **The copies had already drifted**, which is the argument for doing it rather than a tidiness one: the device-key path never recorded `LastSuccessfulSignInAtUtc`, so an attendee who only ever signed in with Face ID looked inactive to the **A1-19 dormant-account sweep** and was a candidate for auto-disable while using the app daily; it also returned no `PreviousSignInAtUtc`, so the "last signed in …" notice was blank on that path alone. **Fix:** `ITokenIssuer` + a single `TokenIssuer` in `SIMF.Application.IdentityAccess`, owning the claim set, the refresh-token row and the D-443 cap. Both call sites now delegate; what stays with them is the entry-point-specific audit row (`SignIn.Succeeded` vs `SignIn.WithDeviceKey`) and its log line, which genuinely differ. Badge-QR sign-in needed no change — it already delegates to `SignInService.SignInAsync`, and the parity test pins that so the delegation cannot be replaced by a third copy. `secondFactorCompleted` is `bool?`: the password paths state `true`/`false` (held-item #2c), the device-key path passes `null` to keep its existing `TwoFactorEnabled`-derived `amr`, because a signed challenge is a possession factor rather than one of the three that flag describes. **Deliberately NOT routed through it:** `SessionService.RefreshAsync`. Rotation must inherit the presented chain's absolute deadline instead of starting a new one (D-443) and runs in its own transaction with `RotatedFromId` — a different lifecycle, not a duplicate of this one. **Test:** `tests/SIMF.Api.Tests/TokenIssuerParityTests.cs` compares claim **types** (not values — `sub`, `jti` and the `amr` strength marker legitimately differ per sign-in) and the persisted refresh-token window across password, badge-QR and device-key sign-in, and asserts the device-key path now records the account as active. No contract change: `PreviousSignInAtUtc` already existed on `AuthTokens` and merely stops being null on one path. | The stated defect was "duplicated minting", but the reason it matters is that a duplicate is where a security control quietly stops applying. The dormant-sweep divergence had already happened and nothing failed; a future claim or a change to the 24h cap would have gone the same way. |
