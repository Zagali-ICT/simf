# C2 — `OA-D5` — meeting check-in stamps recorded but never exported

## DECISIONS_LOG

### D-NEXT — Meeting hall check-in stamps reach the grids and a delegation export (OA-D5)

**Context.** Both meeting desks have had a check-in action for a while
(`POST /admin/speaker-meeting-requests/{id}/check-in`,
`POST /admin/delegation-meeting-requests/{id}/check-in`) and both stamp `CheckedInAt`
+ `CheckedInByUserId`. Neither stamp reached any report:
`AdminSpeakerMeetingRequestRow` had no `CheckedIn*` member at all, the speaker XLSX
shipped exactly six columns (Speaker, Requester, Subject, Status, CreatedAt,
RespondedAt), and the delegation desk had **no `/export` route whatsoever**. "Who
actually turned up" was unanswerable off-screen.

**Decision.**

1. Append `CheckedInAt` + `CheckedInByName` to `AdminSpeakerMeetingRequestRow` and
   `AdminDelegationMeetingRequestRow`.
2. Project them in both list services, resolving the operator's display name through
   `IIdentityUserDirectory.GetDisplayNamesAsync`.
3. Add `CheckedInAt` + `CheckedInBy` columns to the speaker export.
4. Add `ExportDelegationMeetingRequestsEndpoint`, the export the delegation desk
   never had, gated on the new `PermissionCatalog.DelegationMeetings.Export`.

**Consequences / constraints honoured.**

- **Append-only wire (D-219).** Both members are appended with `null` defaults, so
  the shipped mobile/CP JSON contract is unchanged for any client that does not know
  them.
- **No cross-database JOIN (D-157).** `CheckedInByUserId` is a bare logical `Guid`
  into `SIMF_Identity`. The name comes from ONE Identity query per page, merged in
  memory; rows with no check-in contribute no id to it. A deleted operator account
  simply yields a null name — the timestamp is the audit fact and survives.
- **`Export` split from `View`.** Same reasoning as every other export gate in the
  catalogue: taking a spreadsheet of meetings off the premises is a bigger act than
  reading a page of them on screen.
- **Requester email stays out of the export**, matching the speaker export's existing
  D-185 posture — it is per-record PII surfaced only via the audited detail endpoint.

## Follow-up (not in this changeset — Control Panel files, outside Track C)

The API side is complete and gated. The CP still needs, in
`src/ControlPanel/SIMF.ControlPanel/`:

1. `CheckedInAt` + `CheckedInByName` columns on the speaker and delegation
   `SimfDataGrid`s.
2. An Export button on the delegation meetings page wrapped in
   `<AuthorizedAction Permission="PermissionCatalog.DelegationMeetings.Export">`.
3. The BFF plumbing that button needs — a `SimfAdminClient` method plus an explicit
   `AccountEndpoints` map for `/admin/delegation-meeting-requests/export`. The CP is a
   BFF with no catch-all proxy, so without both it compiles and 404s silently.

No permission work is outstanding: `DelegationMeetings.Export` is already in
`PermissionCatalog.All` (added by the Prep agent) and therefore already seeded.
