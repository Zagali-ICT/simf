# Pending global-doc merges — `#2d` (Track A, item A2)

`AdminAccountService.CreateAccountAsync` never forced `TwoFactorEnabled` for
Admin-typed accounts, so a CP-provisioned admin could stay permanently
single-factor. Hard-blocked on A1 — see below for why shipping it alone is worse
than the defect.

## DECISIONS_LOG

| D-NEXT | 2026-07-31 | **Admin creation forces `TwoFactorEnabled`, conditioned on the enrolment path being live (`#2d`).** `AdminAccountService.CreateAccountAsync` created every account with the Identity default (`TwoFactorEnabled = false`), so an admin provisioned from `/admin/admins` never had a second factor unless they went and enabled one on `/account/profile`. **Fix:** for `userType == UserType.Admin`, `accounts.SetTwoFactorEnabledAsync(user, true)` right after the create succeeds. **The condition is the point.** `SignInService` selects the factor as `authenticatorKey != "" \|\| roles.Count > 0 ? Totp : EmailOtp`; a newly created admin has a role and no key, so setting this flag on its own challenges them for a TOTP code against a secret that does not exist — a **permanent lockout at creation**, worse than the single-factor defect it fixes. The flag is therefore gated on `IdentityLifecycle:RequireControlPanelTwoFactorEnrolment`, the same setting that arms the `#2` enrolment branch: when the way in is switched off, the flag is not forced. That encodes the documented `#2 → #2d` sequencing in code instead of leaving it as a note in a plan, and it is why the general test suite (which pins the setting off) is unaffected while production gets both halves. `AdminAccountService` gains `IOptions<IdentityLifecycleOptions>`; no schema change, no contract change, no new permission. **Test:** `ControlPanelTwoFactorEnrolmentTests` asserts both halves — that a created admin carries the flag, **and** that they can still complete a first sign-in end to end (invite → set password → approve → sign in → enrol → session with `amr=mfa`). A test that only checked the flag would have passed while every new admin was bricked. | The register's own sequencing note (2026-07-30) says `#2d` on its own is worse than the defect it fixes. A comment saying so is not a control; a condition that makes the unsafe combination unreachable is. |
