# C5 — `FR-803` — no >=80% match-score threshold and no auto-recommendation push

## DECISIONS_LOG

### D-NEXT — FR-803 match threshold + batched auto-recommendation push

**Context.** `RecommendationService` sorted by score and simply `Take`-n'd the top N.
There was no threshold constant and no `0.8` comparison anywhere in the file, so the
weakest possible overlap ranked as a "recommendation" whenever nothing better existed.
`NotificationKind` had no match value across 0-58, and no worker pushed anything.
Owner answer **Q8**: build to the stated 80%.

**Decision.**

1. `RecommendationService.StrongMatchThreshold = 0.80`, `NormaliseScore`, and a new
   `IRecommendationService.StrongMatchesAsync`.
2. `NotificationKind.MatchRecommended = 60` (additive, persisted by name — added by
   the Prep agent).
3. `MatchRecommendationPushWorker`, a batched poll worker beside `SessionReminderWorker`.

**The browse read is deliberately left alone.** `MeetPeopleLikeYouAsync` still returns
the best N regardless of strength, which is correct for a surface the user chose to
open. The threshold governs only what the system may **interrupt** someone with. Two
different questions, two different answers.

**Why the score is clamped.** The raw score is Jaccard overlap plus a
`SameProfileTypeBonus` of 0.05, so a perfect match scores 1.05. "80%" is a percentage
and has to be compared against something that cannot exceed 1.0, hence
`Math.Clamp(score, 0, 1)`. The same-tier bonus stays inside the comparison on purpose:
at equal overlap a candidate in the caller's own tier IS the better match — that is
the entire reason the bonus exists.

**Batching over exhaustiveness.** The ranker does a full candidate scan per caller, so
scoring the whole roster in one tick would be O(n²) in a burst. Each tick takes 25
callers ordered by user id, resuming after the previous tick's last id and wrapping at
the end; over a few hours the roster is covered. The cursor is in-memory on purpose —
losing it on restart costs nothing.

**Dedup: the D-713 dispatcher guard, not a stamp table.** The requirement is once per
`(caller, candidate)` pair, which is exactly
`DeduplicateByRelatedEntity` keyed on the candidate's profile id. Re-running a batch
is a no-op, so no stamp column, no migration, and no crash window.

**Privacy.** `ShowInMeetLikeYou = false` is honoured at **batch selection** — before
the ranker ever sees the caller — as well as inside the ranker's candidate query. An
opt-out must not merely hide someone from others; it must also stop the system
messaging them.
