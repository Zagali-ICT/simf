# C7 — `sms-whatsapp-channels` — no channel abstraction behind the dispatcher

## DECISIONS_LOG

### D-NEXT — `INotificationChannel`: the delivery seam behind the notification dispatcher

**Context.** The implementation-gap report credited notifications with "one
abstraction". It did not generalise past email:
`NotificationDispatcher.DispatchAsync` hard-coded two deliveries — write the in-app
`Notification` row, then, if `SendEmail`, resolve the address and enqueue an email.
A third transport could only be added by editing the dispatcher. A case-insensitive
search for `sms|whatsapp` across the backend returned exactly one unrelated hit (the
word "mechanisms").

**Decision.** Introduce `INotificationChannel` (`Name`, `Order`, `ShouldHandle`,
`SendAsync`) with two implementations — `InAppNotificationChannel` (Order 0, handles
everything) and `EmailNotificationChannel` (Order 10, handles `SendEmail = true`).
The dispatcher iterates the registered channels in ascending `Order` and keeps
exactly one responsibility: the D-713 one-per-(user, kind, entity) dedup guard.

**Consequences.**

- **A move, not a rewrite.** The row-building and email-sending code was lifted
  verbatim into the two channels, so every existing notification behaves identically.
  `NotificationLifecycleTests` (trigger by trigger) is the acceptance test for that
  claim and is unchanged.
- **The dedup guard stays in the dispatcher**, not in a channel: it is policy about
  the dispatch as a whole. Put in a channel, every future transport would have to
  re-implement it and they would drift.
- **`Order` is explicit**, not implied by DI registration order, so the in-app row is
  always written before any outbound transport and no transport failure can cost the
  user their in-app record.

**Scope — deliberately no SMS or WhatsApp channel.** Both need a procured gateway,
which is an owner-action item, and a stub that silently drops messages would be worse
than none. The deliverable is the seam: when a provider is chosen the whole change is
one new class implementing `INotificationChannel` plus one line in
`DependencyInjection`. The dispatcher does not change again.
